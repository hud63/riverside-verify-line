# Observability: what I can see beyond log lines

All numbers below are real, pulled from the `verify-line` Edge Function and `CallerSession` actor on 2026-11-14 (last-24h window). Each comes from a platform-generated signal, not from my own `console.log`.

## 1. Function metrics (`telnyx-edge metrics verify-line`)

| Signal | Value |
|---|---|
| Requests | 1,512, **100.0% 2xx**, 0 client errors, 0 errored |
| Latency p50 / p95 / p99 | **3 ms / 134 ms / 1,011 ms** |
| Avg duration | 37 ms |
| CPU avg / max | 44m / 80.6m |
| Memory avg / max | 1,001 MiB / 1,888 MiB (limit 7,680 MiB) |

**What it told me:** the p99 of about 1 s is not random. It lines up with the `/dv` call-start webhook's own timing field, `kvMs: 1029` and `kvMs: 1041` on real calls. So the slow tail is the **KV flag read at call start**, not the actor or the MCP tools. That was one measurement away, because every log line records `kvMs` and `actorMs` separately (`timed()` in `src/index.ts`).

**Next step I'd take:** cache the two flags in memory for about 30 s per function instance, or read them in parallel with a short timeout and fall back to defaults. The fallback already exists: a KV failure is caught, logged as `kvError`, and the call proceeds with transfers on.

## 2. Actor metrics (`telnyx-edge actors metrics CallerSession`)

| Signal | Value |
|---|---|
| Actor requests | 85, **100.0% success** |
| Latency p50 / p95 / p99 | **69 ms / 213 ms / 244 ms** |
| Avg duration | 67 ms |

This confirms that the per-caller state (attempt counter, lockout, member hand-off, callback alarm) is not the bottleneck. Even the p99 is about a quarter of a second.

## 3. Actor invocation logs (`telnyx-edge actors logs CallerSession --type invocations`)

The platform writes one record per actor method call, including alarm deliveries, whether or not my code logs anything:

```
21:09:12.233Z  <caller>  __alarm__  ok  127ms
21:17:57.800Z  <caller>  __alarm__  ok   71ms
21:24:01.299Z  <caller>  __alarm__  ok   73ms
```

Method mix in the current window: `beginCall` ×5, `recordAttempt` ×4, `rememberMember` ×1, `getMemberId` ×1, `scheduleCallback` ×1, `__alarm__` ×1.

**Why it matters:** this is how I proved the callback alarm fires on time (due 21:09:12, fired 21:09:12). The handler's own `console.log` goes to the **actor runtime** stream, not the function log. See the bonus story in `debugging-narrative.md`.

## 4. State read-backs built into the request logs

Two fields make the *stored* state visible on every request, so I don't have to infer it:

- `schedule_callback` logs `alarmInMs` (from `ctx.storage.getAlarm()` right after setting it): proof the alarm is armed, e.g. `119836`.
- `/dv` (call start) logs `pendingCallback: {status, dueAt, alarmAt}` for the caller: proof an earlier alarm ran (`status: "due", alarmAt: null`).

## 5. The proof chain in the conversation transcript

- `get_plan_benefits` returns `member_source: "conversation"`. This proves the specialist got the member ID from server-side state keyed by Telnyx's `_meta.telnyx_conversation_id`, not from the prompt and not from the caller repeating it.
- `coverage_status` and `spoken_reference` are generated by the server, so what the assistant says can be checked against the tool output line by line.

## 6. Logs and support operations

| Command | Use |
|---|---|
| `telnyx-edge logs verify-line --since 20m` | function logs: one structured JSON line per request (`requestId`, `route`, `action`, `outcome`, `kvMs`, `actorMs`, `totalMs`, masked `callerId`) |
| `telnyx-edge actors logs CallerSession --type runtime` | actor `console.log` (alarm `callback_due`) |
| `telnyx-edge deployments verify-line` / `revisions` / `rollback` | what's live, why a deploy failed, roll back |
| `telnyx-edge log-export` | push logs to an external sink (Datadog, S3, …) for retention and alerting |
| `POST /admin/reset` (`x-admin-token` from KV) | support action: clear a caller's lockout; logs `hadLockout` |

**PII rule held throughout:** phone numbers are logged as `***` plus the last 4 digits, member IDs never appear in function logs, and DOB is never logged.
